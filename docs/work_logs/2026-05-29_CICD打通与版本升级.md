## 二、问题与修复详情

### 1. Tauri 产物名与 CI 期望不一致

**现象**：`build-tauri` job 显示成功，但 `package-installer` 报 `Artifact not found for name: tauri-app`。

**根因**：
- `upload-artifact` 在找不到文件时只 warning 不 fail，导致 build job 假绿。
- Cargo 默认按 `package.name = "hermes-desktop"` 产出 `hermes-desktop.exe`，而 workflow 和 `.iss` 都期望 `Hermes.exe`。
- `tauri.conf.json` 的 `productName: "Hermes"` 只影响 NSIS 安装包展示名，不影响 Cargo 二进制名——这两条链路解耦，是踩坑根源。

**修复**：
- 按用户偏好，统一使用 `hermes-desktop.exe` 作为产物名与安装名（`MyAppExeName`）。开始菜单/快捷方式显示名仍由 `MyAppName="Hermes"` 控制，用户体验不受影响。
- 给所有 `upload-artifact` 步骤加 `if-no-files-found: error`，杜绝"路径不匹配却假绿"的隐患。

### 2. Inno Setup 缺少简体中文语言文件

**现象**：`Couldn't open include file "...Languages\ChineseSimplified.isl"`，编译中止。

**根因**：Inno Setup 将语言分为 official（随安装包分发）与 unofficial（社区维护，需单独下载）两类。中文/日文/韩文等均属 unofficial，GitHub runner 镜像里的 Inno Setup **不含**这些文件。`Minionguyjpro/Inno-Setup-Action` 只是直接调用镜像预装的 `iscc.exe`，不会补装语言。

**修复**：在 `package-installer` job 中、Inno Setup 编译前增加一步，从官方 `jrsoftware/issrc` 仓库下载 `ChineseSimplified.isl` 到编译器的 `Languages\` 目录。`.iss` 文件无需改动。

### 3. layer-browser 超 GitHub 2GiB 单文件上限

**现象**：`Create Release` 上传 `layer-browser.tar.gz` 报 `size must be less than 2147483648`。

**根因**（两层）：
- **体积本身偏大**：browser 层装 Node.js + Playwright + Chromium，约 1GB。
- **存在严重冗余**：`build_layer()` 原本导出的是完整镜像 rootfs（含 core 的 ~400MB），并非真正的差分层。`layer-browser.tar.gz` 中有 1.4GB 与 `rootfs-core.tar.gz` 重复。

**修复**（两条正交优化叠加，经用户确认一起做）：

1. **真正的差分层**（去冗余）：新增 `wsl-distro/export-differential-layer.sh`——导出 core 镜像的文件路径清单，解压 layer 镜像，按路径剪除 core 已有的文件，只打包 layer 独有内容。`build-rootfs.sh` 与 CI 复用同一脚本（单一真相来源）。脚本刻意放在 `wsl-distro/` 而非 `wsl-distro/scripts/`，避免被 cp 进 docker build context 后混入 rootfs。

2. **减肥**（削绝对体积）：
   - `Dockerfile.core`：删 `__pycache__`/`*.pyc`、pip/uv 缓存、docs/man、非英文 locale。**必须在 core 层做**——字节一旦进入 core image，下游 layer 再 `rm` 也无法缩小 layer 体积。
   - `Dockerfile.browser`：仅装 Chromium（不装 Firefox/WebKit），`--omit=dev` 安装 npm 依赖并清缓存。
   - `Dockerfile.voice`/`messaging`：清各自引入的字节码与缓存。

### 4. hermes-agent 升级 v0.15.0 → v0.15.1（紧急补丁）

**背景**：上游发布 v0.15.1（tag `v2026.5.29`），紧急修复 v0.15.0 的 dashboard 401 无限刷新循环（loopback 模式下首次安装即触发）。

**关键发现**：v0.15.1 本身无"瘦身"宣传，但其 `pyproject.toml` 在 2026-05-12（供应链蠕虫事件后）做了依赖重构，将一批 provider-specific 包从 `[all]` 剥离到 lazy-install（首次使用时联网装）。这对本项目有直接影响——会破坏 standalone 的**离线**承诺。

**处理**（升级 + 用 extras 显式补齐）：
- `AGENT_VERSION` → `v2026.5.29`。
- `Dockerfile.core`：显式补装被剥离的 `[anthropic,exa,firecrawl,parallel-web,fal,edge-tts]`，确保离线可用。
- `Dockerfile.voice`：改用 `.[voice,tts-premium]` extra（替代手写包列表，版本由上游统一管理）。
- `Dockerfile.messaging`：改用 `.[messaging,dingtalk,feishu,wecom,bedrock,azure-identity]`；anthropic 与 web-search 后端已上移 core，不再重复装。
- 16 个 extra 名均已对照上游 `pyproject.toml` 核实存在；确认 `[all]` 不含 voice/messaging（各层保持互斥）。

### 5. 差分层导出脚本 CI 中 tar 失败

**现象**：差分逻辑正常（`pruned ~21770 files, ~1086 MiB`），但最后 `tar` 报 `output/layer-xxx.tar.gz: Cannot open: No such file or directory`。

**根因**：脚本 `cd` 进临时工作目录后，`tar` 用的是调用方传入的**相对路径** `output/layer-xxx.tar.gz`，于是解析到了工作目录下不存在的位置。

**修复**：将"相对路径转绝对路径"的逻辑移到**脚本最顶部**（任何 `cd`/`mktemp`/heredoc 之前）。首版修复曾把该逻辑放在 Python heredoc 之后，CI 环境下未稳定生效；移到顶部后彻底解决，并加 `echo "Output path:"` 便于后续排错。
