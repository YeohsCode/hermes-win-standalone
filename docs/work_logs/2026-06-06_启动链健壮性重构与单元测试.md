## 二、问题与修复详情

### 1. WSL 进程生命周期根因：nohup 进程随 wsl.exe 退出被杀

**现象**：每次安装后启动均失败——"Hermes did not become ready within 120 seconds"。PID 文件存在但进程已死亡，日志文件为空（0 bytes）。

**根因**：WSL 的进程管理机制——通过独立 `wsl.exe` 调用启动的 `nohup` 后台进程，会在该 `wsl.exe` 退出时被终止。原代码分两步执行：
1. `spawn_session`: `wsl -d HermesLinux -- tail -f /dev/null`（keep-alive）
2. `exec`: `wsl -d HermesLinux -- bash start-services.sh 8787`（启动服务）

第二个 `wsl.exe` 进程退出后，其内部的 nohup 子进程（agent + webui）被杀死。keep-alive 只能保持 VM 不关闭，无法保护另一个 session 内的进程。

**验证**：通过对照实验确认——`nohup sleep 777` 在独立 `wsl.exe` 中启动后消失，而 `nohup sleep 999` 在同一 session 中启动后存活。

**修复**：将启动脚本和 keep-alive 合并到同一个 `wsl.exe` 会话：
```
bash start-services.sh 8787 > /tmp/hermes-start-output 2>&1;
echo $? > /tmp/hermes-start-exit;
exec tail -f /dev/null
```
脚本输出和退出码通过临时文件捕获，Rust 侧轮询读取。

### 2. HTTP 健康检查仅接受 200

**现象**：WSL 内服务已启动，端口已监听，但 `wait_for_http_ready` 永远不返回成功。

**根因**：WebUI 的 `/` 路径返回 HTTP 302 重定向（跳转到登录页），原代码 `code.trim() == "200"` 判定为未就绪。

**修复**：改为接受 200-399 范围的 HTTP 状态码。

### 3. 安装器未强制 WSL2

**修复**：`import-distro.ps1` 增加 `--version 2` 参数给 `wsl --import`。导入后验证版本，WSL1 自动执行 `wsl --set-version HermesLinux 2` 转换。`check-wsl2.ps1` 增加 `VirtualMachinePlatform` 和 `Microsoft-Windows-Subsystem-Linux` 可选功能的检测与自动启用。

### 4. 三阶段启动诊断 + 自动重试

**修复**：将原来的单一 120 秒超时拆分为三个阶段，每阶段独立超时并携带诊断日志：
- `wait_for_vm(30s)` — WSL VM 是否响应
- `wait_for_service_pids(30s)` — 服务进程是否存在
- `wait_for_http_ready(90s)` — HTTP 端口是否就绪

首次失败后自动执行 stop → terminate → 重试一次，错误信息合并两次失败的诊断。

### 5. 前端实时进度 + 错误操作

**修复**：Rust 侧通过 `emit("hermes-progress", ...)` 推送阶段信息。前端 `Loading` 组件展示当前步骤（"清理旧进程..."、"启动服务..."、"等待 WSL 虚拟机..."等）。错误页新增"查看日志"、"重置并重试"、"直接重试"三个按钮。

### 6. 可测试架构与单元测试

**修复**：引入两层 trait 抽象实现依赖注入：
- **Layer 1 — `WslOps` trait**：抽象所有 WSL 操作，用于 `main.rs` 编排逻辑的测试
- **Layer 2 — `CommandRunner` trait**：抽象 `wsl.exe` 命令执行，用于 `wsl.rs` 内部逻辑的测试

核心函数提取为泛型版本（`start_hermes_attempt<W: WslOps>`、`start_hermes_with_retry<W, P>`、`check_wsl_ready_impl<W>`），Tauri command 层变为薄代理。
